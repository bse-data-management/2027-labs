# Session 3 lab — Relational data management and SQL

The company's database: `zones`, `drivers`, `riders`, `driver_balances`, `trips`,
`payments`. You create the schema, load a month of trips into it, watch it refuse
three statements it ought to refuse, and answer five questions in SQL.

Every question is answerable from one table. Joins are session 4.

## Setup

From the repository root:

```bash
uv sync
uv run python scripts/prepare_nyc_taxi_normalized.py
docker compose up -d
```

Then open **<http://localhost:8888/lab?token=labs>** and click into
`session-03/lab.ipynb`.

The preparation step downloads ~50 MB and writes ~200 MB to
`data/nyc-taxi-normalized/`; it needs internet, and nothing after it does. It is safe to re-run — it skips what it
has already produced. Delete `data/nyc-taxi-normalized/` to start again.

## The parts

| Part | What |
|---|---|

## If you break the database

Run the `reset_database()` cell again. It drops all six tables, recreates them
from `sql/schema.sql`, and reloads the data, in about 20 seconds. Nothing you can
type in Part A will leave you stuck.

## Looking at the schema without SQL

pgAdmin is running at **<http://localhost:5050>** with the connection already
configured. Open *Servers &rarr; labs* — it asks for the password once, which is
`labs` — then *Databases &rarr; labs &rarr; Schemas &rarr; public &rarr; Tables*.
Each table shows its columns, and under *Constraints* the keys and checks you
wrote in the DDL.

Useful for seeing the shape of the six tables. Everything in the lab can be done
from the notebook.

## About the data

Real NYC taxi trips for January 2024, sampled to 1,000,000 rows across the whole
month. Drivers, riders, payments and balances do not exist in the source data and
are generated by `scripts/prepare_nyc_taxi_normalized.py`, consistently enough
that every foreign key holds on the first load. Zones are the city's own lookup table.
